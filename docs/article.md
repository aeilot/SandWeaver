# 一个沙盒可以接力多少次？

在一个 coding agent 会话里，执行和等待交替出现。Agent 跑一次测试，拿结果去问模型，回来改代码，再跑一次。开发服务器可能要跨好几轮调用一直活着。任务结束后，这些临时进程通常已经没有价值，但下一项任务还可能需要同样的工具和依赖。

SandWeaver 把这几个时间尺度拆开。Agent 在容器外持有会话和模型配置。独立调度器通过本机 Unix socket 分配 Docker worker。一个租约覆盖同一任务的多次命令。租约结束，项目文件留在宿主工作区，任务的进程空间和文件系统写层被回收，worker 回到池里。池按实际需求增长，空闲后收缩。整个路径可以在本机运行。

## 接力时换什么

最早的池把用过的容器删除，再起一个填回去。在持续请求下，这相当于把启动成本从领取挪到归还。补位来不及，队列还是会等。另一种做法是保留容器并清理，但任务通过 shell 可以修改用户目录、全局依赖和仓库以外的文件。清理规则很难靠列举目录覆盖完整。

当前设计在任务开始前就把这些写入放进 OverlayFS 可写层。每个租约还有自己的 PID namespace。下一任务用同一份预装基础环境，拿到新的可写层与进程空间。需要长期保留的项目文件通过单独挂载留下。临时安装的包会随写层丢弃。若这部分安装值得跨任务复用，需要另建经过验证的只读环境。

## 我们测到了什么

在单 worker 的本地实验里，两组使用同一热镜像，交错跑了 12 轮。删除 A 再创建 B 的交接中位数是 147 ms，保留 worker 并重建任务视图是 43 ms。两组都验证了 B 能使用预装依赖、看不到指定的残留文件、连不上 A 的服务。常驻 worker 首次准备另花了 1.61 秒。这个实验测的是固定命令的交接，未计入模型、排队和动态伸缩。

集成测试进一步验证了同一个 worker 可以接力、同租约能保留后台服务，以及并发负载能让池从 1 扩到 2 再缩回 1。OpenHands SDK 已经能通过这个路径调用 shell。真实模型的完整 coding task、对抗性任务隔离和等资源的持续负载对照仍待验证。

## 这个设计还需要回答什么

[Sandman](https://arxiv.org/html/2610.39711v1) 已经说明沙盒接力会遇到一个实在的问题。上一个任务留下的状态会改变下一个任务的评分结果。它通过检查和恢复来减少这类错误。SandWeaver 值得测的是，预先划定可丢弃的状态边界，能否减少交接时的检查与回退，同时让下一任务得到和干净环境一致的结果。

下一轮实验应该用相同镜像和负载，把热镜像重建、检查后清理、丢弃任务视图放在同一个调度器里比较。让 A 有意覆盖基础文件、改包元数据和启动后台服务，再用从未复用的环境给 B 做对照。记录 P95 等待、错误通过、回退率和资源占用。如果 43 ms 的优势进入真实队列后消失，或者正确性依赖无法维持的假设，就应该把结论限定在微基准。若它仍能降低等待并保持结果一致，才能进一步研究哪些执行状态值得留下。
