# Coding agent 的 worker 复用实验

在固定执行资源预算下，coding agent 能否保留独占工作区和必要状态，把 worker 让给其他会话，再在下一批工具就绪时继续正确执行？我们同时关心排队、成功完成的任务吞吐和会话尾延迟。扩缩容是下一组对照，容量增加后还要核算 worker-seconds。

目前验证了可信本机任务上的热 worker 交接、OpenHands 按批次和按需领租，以及两种可挂载缓存的恢复成本。多条真实轨迹下的吞吐、高并发下的尾延迟和跨租户隔离仍待验证。[设计与实现](architecture.md) · [相关工作与研究计划](research.md)

## 真实 agent 观测与可归还边界

一次 OpenHands/DeepSeek Flash Python 修复成功通过 5 项独立测试。全会话租约持续 14.328 s。六次模型客户端调用分别为 1.434、1.379、0.830、3.727、2.719、3.687 s，合计 13.776 s，约占租约的 96.2%；六次 shell 往返合计 346 ms。模型区间包含 SDK 和网络，表示可能的归还窗口。该轨迹未测后台进程存活，可回收比例需要独立核验。[完整观测报告](agent-observation.md)

跨批次边界按下一批需要的状态判断。代码编辑、一次性测试、增量构建、代码生成等，可以在文件和依赖完整挂载后重启。常驻服务、交互式终端、活跃连接、未完成操作，以及仅存在于旧写层的必要文件，需要保持租约或显式恢复。会话必需产物保留至会话结束或不再可恢复。可重建缓存可以在容量允许时保留，在字节数或 inode 触及预算时淘汰无活跃挂载的缓存。缓存预算和回收器属于设计提案。当前实验将缓存放在宿主工作区内。[状态表](architecture.md#设计目标)

## 热交接和旧写层删除

历史热镜像对照中，销毁 A 容器并创建 B 的交接 P50 为 147 ms，复用 worker 并重建写层及进程空间为 43 ms。交接从 A 完成到 B 首条验证完成。从 A 启动算起是 274 和 93 ms，首次 worker 准备约 1.61 s。以下 cleanup 对照使用自己的时序、镜像和基线。[历史交接记录](experiments.md#独立仓库内可以复现的结果)

在 OrbStack Linux/aarch64、`sandweaver-demo:local` 和同一个热 worker 上，两组都先确认 A 进程退出，再把旧写层移到待回收目录。同步组等删除完成后归还，延后组从 RESET shell 启动后台删除。每种负载每组预热 1 轮、交替测 30 轮。首次 worker 准备 849 ms。下表为 P50 / P95，单位 ms。

| 负载 | 删除 | A 归还 | B 领租 | A 开始归还到 B 验证完成 | 实际删除 |
|---|---|---:|---:|---:|---:|
| 无额外文件 | 同步 | 52.00 / 60.57 | 56.22 / 64.90 | 154.12 / 169.84 | 0.60 / 0.74 |
| 无额外文件 | 延后 | 50.97 / 55.75 | 55.61 / 60.91 | 149.88 / 165.15 | 0.57 / 0.75 |
| 8,192 × 4 KiB | 同步 | 61.85 / 67.08 | 55.91 / 60.61 | 157.54 / 168.28 | 9.79 / 10.60 |
| 8,192 × 4 KiB | 延后 | 62.54 / 65.99 | 54.70 / 62.16 | 158.54 / 168.44 | 9.83 / 10.45 |
| 4 × 8 MiB | 同步 | 52.83 / 58.07 | 56.68 / 62.84 | 151.57 / 160.51 | 1.80 / 2.29 |
| 4 × 8 MiB | 延后 | 53.67 / 58.68 | 54.75 / 62.39 | 151.07 / 166.61 | 1.86 / 2.24 |

端到端逐轮配对的差值中位数为 −1.67、+0.04、−1.22 ms。另一次每组 12 轮的诊断中，从发出 kill 到确认退出 P50 约 24–26 ms。小文件组把 RESET shell P50 从 34.88 降到 24.77 ms，但宿主侧 `docker exec` 扣掉 shell 内时间的余量从 28.66 增到 37.62 ms。延后组 36/36 次删除都在 B 启动脚本之前完成。当前后台删除方式未稳定缩短交接，也未观察到删除与 B 启动的重叠。连续回收积压及 Docker 内部等待原因仍待测。生产 RESET 直接删除 `/state/task`，两组的目录移动仅用于控制变量。

## 换 worker 后的状态与缓存

固定两个热 worker，强制在另一台 worker 恢复。工作区文件和工作区内的 Python 模块可继续读取，旧 `/tmp` 模块和后台服务随租约清除。两种缓存对照每组各 12 轮，运行同一条命令并验证结果。表中命令往返从发出到返回，领租和单独的二进制验收不在表内。

| 工作负载 | 保留缓存 P50 / P95 | 从空目录重建 P50 / P95 | 配对节省中位数 | 缓存占用 |
|---|---:|---:|---:|---:|
| Python 字节码，导入标准库和 humanize | 75 / 103 ms | 271 / 325 ms | 198 ms | 132 文件，约 3.1 MiB |
| Rust 1.85.1，离线 Cargo dev build，只修改应用 crate | 140 / 159 ms | 256 / 307 ms | 113 ms | 94 文件，约 13.3 MiB |

Rust 两组分别编译 1 和 7 个 crate，保留组复用了 6 个库 crate。Rust 基准临时在租约内挂载 procfs 以提供 `/proc/self/exe`。结果只覆盖这两个合成负载，库修改、真实依赖图、缓存淘汰和共享存储压力另测。

同一脚本的固定容量回放里，830 ms 近同步场景的短任务完成 P50 从 1004 降到 93 ms，归还方就绪至工具完成 P50 从 71 增到 151 ms。分段复测得到恢复领租 P50 107 ms，其中启动租约的 `docker exec -d` P50 60 ms，就绪探测的 `docker exec` P50 45 ms。72 次重新领租的探测均一次成功；启动和探测仍包含 Docker 命令及运行时开销，未分解 namespace、挂载或 TCP 重连。

## OpenHands 租约策略对照

真实 SDK 和 Docker 运行固定工具序列，本地模拟模型响应。两个热 worker 服务两个 OpenHands 会话。竞争组在两会话进入第二次模型请求后的 50 ms 提交一个短任务。短任务从发出领租请求计到首条命令返回。会话恢复从 SDK 的模型调用结束计到下一条工具命令返回，包含工具分发和重新领租。模型等待是实验配置。最近秩 P95 在每组 9 个短任务样本时等于最大值。

第一轮每组 12 轮，比全会话持租和每批归还。150 ms 等待下，短任务完成 P50 为 329 → 111 ms，会话恢复 P95 为 62 → 131 ms。830 ms 等待下分别为 1009 → 122 ms、70 → 206 ms。830 ms 组重新领租 P50 101 ms，恢复排队 P50 为 0 ms。首次 claim 的计时位置随策略变化，跨策略优先比较恢复或首条工具完成到末条工具完成。[第一轮原始样本](results/openhands-batch-leases.json)

第二轮加入按需归还，每个场景每组预热 1 轮、正式测 9 轮，共 81 轮。

| 场景 | 指标 | 全会话持租 | 每批归还 | 按需归还 |
|---|---|---:|---:|---:|
| 830 ms，无竞争 | 会话恢复 P95 | 84 ms | 156 ms | 71 ms |
| 830 ms，有竞争 | 短任务完成 P50 | 1015 ms | 117 ms | 160 ms |
| 830 ms，有竞争 | 会话恢复 P95 | 70 ms | 144 ms | 144 ms |
| 150 ms，有竞争 | 短任务完成 P50 | 319 ms | 113 ms | 145 ms |
| 150 ms，有竞争 | 会话恢复 P95 | 65 ms | 148 ms | 191 ms |

无竞争时，按需组 18/18 次直接恢复原租约。830 ms 有竞争时，每轮只回收一个 worker，保住原租约和被回收会话的恢复 P50 分别为 66 和 135 ms。短任务承担的按需 reset P50 约 46 ms。150 ms 有竞争时，9 轮中有 3 轮两个原会话都失去租约，先被回收的会话恢复时又触发了第二次回收。这个结果支持比较有界等待和原租约保护，但尚不能定出通用阈值。

Docker/OpenHands 集成测试验证了同批工具保留临时文件、A 等模型时 B 接手、A 在另一 worker 恢复文件、等待期间拒绝重叠路径、按需标记及回收。单元测试验证了 reset 失败时的工作区保护，以及恢复请求等待进行中的回收。
